# Closeout delivery attribution

[pm-ado issue 33](https://github.com/unbraind/pm-ado/issues/33) compares the earlier gap-reporting PR 16 with delivery PR 19. PR 16 lists the statement-enforcement item in a `PM:` follow-up list and says enforcement remains open. PR 19 declares its primary work with a standalone `PM item:` line. The retained minimal public fixtures preserve these relevant body shapes.

| PR body or evidence | Matcher result |
| --- | --- |
| Closing keyword before a canonical tracker link | Declares delivery |
| Whole-line closing keyword plus exact item ID | Declares delivery |
| Whole-line `PM item:` plus canonical link or exact ID | Declares delivery |
| Whole-line `pm-github:` plus exact ID | Declares delivery |
| Undeclared canonical body link, including a gap report, follow-up list, or `tracked in` reference, for an otherwise eligible item | `not_delivery`: Mentioned, not delivered |
| Tracker PR URL metadata with no body reference or declaration | No row |
| Closing declaration for a longer ID with the same prefix | Does not deliver the shorter ID |
| Several linked merged PRs | One explicit `delivery-pr:<canonical PR URL>` item tag wins; otherwise require exactly one claim strictly after the last acceptance-criteria edit; unresolved cases become `needs_review` with all candidates |
| No eligible declaration | No closeout |

Declaration keywords are close, fix, resolve and deliver, including their existing tense forms. Whitespace between declaration and ID is horizontal; a newline cannot join them. Canonical links retain repository, encoding, traversal and exact-ID checks. `PM:` contextual lists do not act as `PM item:` declarations.

The complete selected PR set is evaluated before SDK writes. A `delivery-pr:` tag is an explicit item-owned delivery link and can supply attribution without a body declaration. Multiple tags or a tag outside the selected set cannot silently fall back. Generic `pr_url` metadata remains contextual. Without an explicit delivery link, immutable SDK history determines the last acceptance-criteria change (or item creation when no later edit exists). Exactly one linked merged PR must claim the exact item in its description or commit messages and merge strictly after that cutoff. Unrelated later edits do not move it. Unavailable history holds delivery.

Passing checks do not resolve attribution. Competing claims, equal merge times and multiple post-criteria claims require review even if one has failing checks. A uniquely attributed PR must still satisfy the existing merge and check policy. The selected PR supplies completed_at, resolution, actual_result, close_reason and the close event consistently. All candidates appear in `needs_review` plan rows and the compact closeout PR body; the item stays open. For an all-held workflow run, a privacy-gated tracker `closeout-review.json` artifact provides a reviewable diff without changing any item or item history.

`test/closeout-selection.test.ts` uses real SDK trackers, deterministic SDK clocks for creation and criteria edits, synthetic PR/commit metadata, `GIT_CEILING_DIRECTORIES`, and a PATH containing no git. It covers one PR, an earlier claim before changed criteria plus later implementation, ambiguity, explicit overrides, missing history, and commit claims. The historical receipts below describe earlier matcher revisions; their latest-merge behavior is superseded by this policy.

## Regression evidence

`node --test test/closeout-attribution.test.ts` uses real SDK trackers initialized by the pinned CLI in temporary directories. The primary scenarios set `GIT_CEILING_DIRECTORIES` to the directory above the tracker and execute closeout with a PATH containing no git executable. They verify:

1. Real-shaped gap PR 16 plus structured delivery PR 19 selects PR 19. Distinct head SHAs, merge SHAs and check names prove that durable fields and the appended close event agree on the selected PR.
2. Mention-only PRs leave the item in progress and append no close event, even when tracker PR URL metadata points at one.
3. A closing keyword for a different ID sharing the item's prefix leaves the mentioned item open.
4. Multiple declarations select the latest passing merge, including a lower-numbered PR merged later and a later PR with failing checks. Equal-time selection is deterministic.
5. Same-line IDs, punctuation, tabs, multiline negatives, case rules, many-item planning and mention-only reporting remain covered. A standalone structured markdown link declares delivery; appended follow-up prose does not. A separate whole-line closing declaration can upgrade an earlier bare link.

Function-only behavioral reversion restores `runCloseout` from `dc86e83`, the actual defective predecessor of the prior attribution fix, while retaining current helpers and tests. Each of the first three regressions fails an assertion with exit 1: the gap PR wins, mention-only closes, and the shared-prefix mention closes. Restoring the current implementation passes. No test-load failure is counted.

A separate function-only reversion to origin/main's attribution implementation makes the latest-merge regression fail: competing delivery claims close zero items. A narrow prefix-broadening mutation in the current function also makes the shared-prefix regression fail directly. Reverting only the structured-link helper to its first implementation also fails the follow-up-prose negative. These controls distinguish the historical mention bug, the remaining selection bug and the exact-ID boundary.

## Incomplete candidates and persistent auto-merge requests

Candidate collection is independent of merge/check eligibility. A linked merged PR with missing or invalid merge facts, head checks, protection metadata, or commit pages remains in the ambiguity set. Unknown merged flags and timestamps also remain plausible; `--since` fetches uncertain listing entries instead of discarding them. Only a validated timestamp can place a claim before the criteria cutoff. Commit pagination must match the PR detail response's declared commit count; missing counts or truncated pages remain unreadable evidence, including a cut that could hide a declaration after a body mention. Unreadable commit sets also retain possible commit-only links when descriptions contain no references. A failed PR read cannot prove linkage is absent, so it conservatively holds eligible active items with the unreadable PR number. Foreign, terminal, explicitly excluded, epic and active-parent items remain ineligible. An explicit valid item-owned delivery link can still resolve competing candidates, but cannot waive its chosen PR's evidence requirements.

Review rows retain every candidate number and `missing_evidence` entries with the PR number, evidence code and safe reason. Missing merge evidence names the affected fields. The compact PR summary and review artifact retain these gaps. Complete evidence of a failing check holds an otherwise uniquely attributed PR; passing another PR never resolves competing claims.

The workflow explicitly calls `gh pr merge --disable-auto` for owned closeout PRs before any guard, installation, evidence query or branch update. Only an existing `autoMergeRequest` is revoked; an unarmed PR needs no disabling mutation. An `always()` cleanup repeats revocation on a hold, no publication, disabled CI, failure or cancellation, including failure after auto-merge was armed during maintenance. It uses the caller repository identity and fixed closeout branch, filters out fork heads, and fails before publication if initial revocation is denied. Successful App runs may arm only after caller checks are dispatched and the review hold is clear. Held PR bodies state that automatic merge is disabled because attribution needs review.

The early-exit audit covers invalid default refs and inputs, dependency/setup failures, evidence refusals, privacy/health failures, invalid publication credentials, no-op publication, push/PR-write denial, disabled or missing caller workflows, dispatch denial, and maintenance failures. Initial revocation protects all pre-publication paths; final cleanup covers failures and cancellation after arming. No existing request is carried across a held update.

The table-driven `incomplete candidate holds attribution` regressions cross merge status, merge SHA, merge timestamp, head SHA, checks, required metadata, PR/commit fetches and pagination failures with another valid claim or none, using real non-git SDK trackers and unchanged-history assertions. `earlier armed auto-merge is disabled before a later hold updates the reused PR` runs the actual workflow bash twice against a stateful GitHub boundary; it verifies revocation before PR editing, final disabled state and the public explanation. `previous auto-merge is revoked on workflow exit` exercises guard, setup, evidence, privacy, no-op, empty-CI, dispatch, maintenance and disable-denial paths.

Fix-only revert evidence is recorded on `pm-github-closeout-attribution`: replacing only `runCloseout` with the pre-round implementation failed the initial 20-case matrix (20 failures, exit 1), including an assertion that one item closed instead of zero. Replacing only both explicit disable operations with no-ops failed the two-run workflow regression with `ERR_ASSERTION` (`true !== false`, exit 1). Both implementations were restored. These controls execute the retained tests and do not count test-load errors as regression proof.


A resolved explicit delivery link cannot leave a `needs_review` row for its closed item. Unreadable PR rows begin as refusals, and only unresolved attribution promotes them to review together with candidate details. Additional real-tracker controls cover six unreadable commit-set conditions with reference-free descriptions, crossed with another valid claim or none; these hold possible commit-only delivery instead of treating missing messages as proof of no link.

Confirmed unmerged PRs discovered while checking uncertain `--since` timestamps use the routine `not_merged` decision. They cannot supply delivery or trigger the workflow's incomplete-merge refusal. `confirmed unmerged references cannot block publication of a unique merged delivery` executes the real workflow with both PR kinds and verifies publication, closure and the compact skip count.

## Item revision binding (review round 2)

Closeout reads an authoritative SDK document for each item before fetching PR evidence. Selection uses that document's metadata and retains its complete `hashDocument` hash, including tags, criteria, annotations, links and body. Immediately before SDK persistence, a request-scoped `beforeMutation` guard compares `context.before` with that hash under the SDK's existing per-item lock. Refusal changes neither the item nor its history. A new read outside the lock cannot substitute for this check.

The pinned SDK 2026.10.20 has no public `close` expected-revision option. `BulkItemUpdateMutation.match` guards updates only; `BulkItemCloseMutation` has no match field. The internal `runWithItemMutationPrecondition` is not exported publicly. The implementation therefore uses the public `runWithActiveExtensions` / `setActiveExtensionHooks` guard API and the ordinary SDK close lock. The upstream API needed is `close(id, reason, { expectedItemHash }, clientOptions)`, with an atomic hash comparison inside the close lock and a stable revision-conflict code. Dependency pins remain unchanged.

On revision refusal, closeout re-runs the full evidence and attribution selection once for that item. A unique fresh selection can close with fresh criteria and provenance; competing claims remain held. A second refusal marks all candidate rows `needs_review` with the revision-change reason. A peer's terminal closure is preserved and reported as `already_terminal`. Re-selection cannot close unrelated items or repeat their closures.

The read-to-write audit covers delivery tags, generic PR links, body/commit declarations, acceptance-criteria chronology, terminal status, annotations and linked resources. Closeout does not independently mutate tags, links, criteria or comments. The main write path is SDK `close`, which writes completion time, resolution, expected/actual results and close reason together with its immutable history event. SDK close can also auto-unblock dependents: those writes compare each dependent's own snapshot under its item lock. A refused dependent write gets one fresh delivery selection or an explicit hold; a new prerequisite cannot be erased by stale unblocking. Normal SDK close validation, ownership and workflow policies remain active. The guard is request-scoped and cannot leak into an independent caller or tracker.

`test/closeout-revision.test.ts` schedules six peer edits (retag, acceptance criteria, second delivery claim, peer closure, comment, linked documentation) at 17 boundaries: the document snapshot, every PR/protection/rules/checks/statuses/commits fetch for two PRs, history read, completed selection, immediately before close, and inside the close lock. All use real SDK operations in a non-git tracker. The locked edits must be refused; successful close history must chain to the final selected revision and retain matching delivery tag, criteria and PR provenance. Additional controls cover a second change, independent concurrent writes, item-scoped retry, a deleted snapshot and four dependent-update scenarios (unchanged, concurrent prerequisite edit, conflict during re-selection and an independently handled closure). The suite contains 110 tests. A real SDK `history_append` barrier also pauses a peer after its item write but before its history append. `verifyHistoryEntries(history, selectedDocument)` refuses mixed document/history revisions, so old criteria chronology cannot authorize new criteria.

A guard-only behavioral revert retains the observers and removes only the locked hash comparison. The retag and dependent-update regressions both fail: PR 1 provenance survives a retag to PR 2, and stale automatic unblocking erases a peer prerequisite. Restoring the comparison passes both tests. The PM comments retain the exact commands and counts.


## One item decision through publication (review round 3)

Candidate evidence and item decisions have different roles. `CheckGate` retains the original merge/check facts. One `ItemDecision` projects the final item outcome onto every candidate row, including incomplete competitors:

| Final item decision | Candidate role | Report action / code | Publication |
| --- | --- | --- | --- |
| Chosen, with complete passing evidence | Chosen PR | `close` / `head_checks_passed` | Closed item and its chosen provenance |
| Chosen, with complete passing evidence | Every other candidate, regardless of evidence gaps | `skip` / `duplicate_selection` (superseded informational) | Routine skip count, without a refusal or review hold |
| Blocking hold | Every candidate | `needs_review` / `needs_review`, all candidate numbers and applicable evidence gaps | Open item and review artifact |

A failed chosen check cannot designate a winner or hide its peers. A close refusal or second revision conflict also projects a hold across the whole item group. Standalone proven mentions remain `not_delivery`; they do not claim delivery. Confirmed unmerged and otherwise ineligible references keep their existing routine decisions. Re-selection replaces the old item decision before publication.

`item decision end to end: <selection> / <competitor> / <peer>` in `test/closeout-workflow.test.ts` has **36 cells**: three selection sources (explicit delivery tag, single post-criteria claim, ambiguous), six competitor states (none, valid, missing merge SHA, failed evidence fetch, failed checks, pagination cut), and two peer schedules (none, retag mid-run). The single-claim case changes acceptance criteria between the two merges. Ambiguity with no competitor uses a delivery selector outside the selected set; otherwise both PRs claim delivery after the criteria cutoff. The peer uses the real SDK to retag to PR 1 during PR 2's evidence fetch, after the item snapshot. A stale attempt that could close must re-select; an already unresolved attempt can remain held.

Each cell runs the real closeout CLI and actual workflow bash through its publication gate, privacy scan, local Git push, and PR-body boundary. It verifies the published tracker bytes and history, one close event or none, closure count, all chosen provenance fields, and the public summary. Exactly one result is allowed: closed item with published chosen-PR provenance, or open item with a published hold listing every candidate. A closure cannot coexist with a refusal or review hold; a held item cannot acquire a close event or request automatic landing. The existing non-git SDK selection/revision tests continue to cover operation without a Git repository.
